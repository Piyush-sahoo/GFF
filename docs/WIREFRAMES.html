JOURNEY 5

The login-gated planning agent

the one you said is essential
"I'm a Series-A lending founder looking for a bank partner and a credit-risk vendor. Three days, 256 sessions — tell me who to meet and what to attend, and let me keep it."

How the agent layers on the matcher that already exists

app/lib/match.ts is already a deterministic grounded matcher. It calls no model. Every reason it returns is built only from terms that literally occur in both the objective and the record. Its own header says the point: "there is no path by which a rationale can be invented — the honesty rule is enforced by construction rather than by instruction." An LLM that re-ranks or re-explains those results throws that away. So the model never retrieves — it only phrases a set that is already fixed and already grounded.

✓ deterministic — no model
objective — profile.lookingFor + interests[]
↓
✓ deterministic — no model
match() + retrieve() → candidate set, each item carrying {id, record, why.terms[], why.fields[]}. Invite-only already excluded here.
↓
✓ deterministic — no model
scheduler — drop invite-only (asserted again), resolve time clashes via overlaps(), cap ~3–4 sessions/day, spread across days
↓ — the plan is already complete and shippable at this point —
⚠ the only model call — optional, removable
narrator — sees only the scheduled items and their why.terms. May reorder and write an outreach note. May not introduce an entity, a fact, or a reason.
↓
✓ deterministic — mandatory gate
validator — drops any entity id not in the candidate set · drops any quoted term not in that item's why.terms · runs the booth/hall regex over all prose · on any failure, ships the deterministic plan unchanged

The degraded path is the grounded path. That is what makes this safe to ship — and it mirrors how /api/chat already returns 503 rather than guessing when GEMINI_API_KEY is missing.

The persistence problem — and the fix

today — these two contradict each other
wheresurvives
My PlanlocalStorage
gff.bookmarks.v1		this browser only

MyPlan tells the user, correctly: "saved sessions live in this browser only — no account, no server, nothing shared." A logged-in, agent-generated plan cannot live there and still be a plan you keep.
Recommended: additive, not a migration.
1. localStorage stays the anonymous store, unchanged. It is the offline-safe path on bad venue wifi — that is a feature, not debt.
2. Add a plans collection in Atlas beside profiles, inside app/lib/profiles.ts (the only file allowed to touch Mongo). Store identifiers only — agendaCode, nameKey, slug — plus the grounded why terms. Never denormalised content, or a rebuilt dataset leaves a stale session title (or worse, a stale description) sitting in Atlas. An id that stops resolving is dropped with a visible note, never rendered from a cached copy.
3. On login with local bookmarks and no account plan, offer an explicit merge — "you have 6 sessions saved in this browser, add them?" Never silent.
4. Signed in, Atlas is the source of truth and localStorage becomes an offline cache.
5. Profile delete (remove(), already one-click) must delete the plan too — same consent lifecycle.

Open decisions — these are yours

D1 · the "Beer Booth Partner" tier URL

One of 20 tier strings contains the word Booth. It's a sponsorship name, not a location, and it already renders as a directory chip today. Minting /exhibitors/tier/beer-booth-partner puts "booth" in a URL on a site whose policy is that booths don't exist here. Recommend: no page for it — it lands in the named-partnerships list rows anyway, so nothing is lost.

D2 · plan conflict across devices

Save sessions on a laptop, then on a phone — what wins? Recommend: last-write-wins on the whole document, with the merge prompt only at first login. Set-union is friendlier but makes a removal on device A silently reappear from device B, which is worse. The alternative is per-item timestamps — more storage, more code.

D3 · should the narrator ship at all?

The deterministic plan is complete and honest on its own. The LLM adds ordering prose and an outreach note — and adds the only fabrication risk in the system. Recommend: build the agent without it first, look at the real output, then decide.

D4 · topic threshold

This plan draws the line at ≥2 sessions = 76 pages. ≥3 gives 23 much denser pages; ≥1 gives 346, of which 270 hold a single row. Recommend ≥2.

D5 · the /now clock zone

Pinned to IST (UTC+05:30) rather than device-local, so an international attendee's phone doesn't show an empty festival. Confirm that's the intent.
